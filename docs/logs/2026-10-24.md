# 2026-10-24

## 循环改成 inbox 驱动的常驻状态机

- **为什么**:旧结构把"一次请求"当成 `run` 里的一个 for 循环,历史 / 待回填调用 / 已产出 item 都是
  run 的局部变量;等工具时外部消息没有入口插进来,状态也隐含在"第几步"里。
- **怎么改**(`packages/agent/src/loop/`):
  - 新增 `inbox.ts`:`Queue<InboxMessage>`,消息只有 prompt / tool result 两种,只收集不解释;
  - 新增 `tool-executor.ts`:常驻 worker,按提交顺序执行一批 `function_call`,结果写回 inbox;
  - 重写 `loop.ts`:`AgentLive` 建层时 `forkScoped` 一个永不退出的引擎,状态为
    idle / generating / waiting;`run` 保持不变(造 `Deferred` → 推进 inbox → 等回答);
  - 回放顺序收敛到"并进 transcript"一处:工具结果按调用顺序紧跟 `function_call`,
    等工具期间到达的新 prompt 排在结果之后;工具轮整批保留(含 `reasoning`);
  - `LlmError` 不再杀死循环:错误交给等回答的 `run`,回到 idle。
- **代价**:`run` 被中断只丢掉回答口,已在飞的生成不会取消(web 断流仍会烧到本轮结束);
  合并轮次的 prompt 共享一次回答,`settings` / `tools` / `observe` 以后一条为准。
  详见 [`../decisions/0009-inbox-loop.md`](../decisions/0009-inbox-loop.md)。
- **验证**:新增两条用例(等工具时插 prompt 的合并顺序、模型报错后循环仍可用);
  `pnpm check` / `pnpm typecheck` / `pnpm test`(6 文件 55 用例)/ `pnpm build` 全绿。
- **落档**:重写 [`../designs/agent/loop.md`](../designs/agent/loop.md),
  更新 [`../designs/overview.md`](../designs/overview.md)、web host 的会话说明与 `AGENTS.md` 现状。

## 跟进:`run` 改成无限循环,消息只从 inbox 进

- **为什么**:上一版虽然把三个实体拆开了,但 `run(input, …) => answer` 仍是请求-应答门面,
  引擎藏在 `Layer.effect` 的 `forkScoped` 里;状态机、服务装配、等回答的逻辑还挤在 `loop.ts`。
- **怎么改**:
  - 状态机搬到 `loop/llm.ts`(`llmStateMachine`),依赖是参数(Llm / inbox / executor),不认识 `Agent`;
  - `AgentShape.run: Effect<never>` —— `run` 就是循环本身,没有 prompt 参数;
  - 消息入口改成 `Inbox.ask(input, settings, tools, observe?)` / `Inbox.offer(message)`;
    循环退出时 `Inbox.close`,还在等的 `ask` 立即失败;
  - `AgentLive` 只装配(输出 `Agent | Inbox`),不 fork;CLI / REPL / smoke / 测试用 `forkChild`,
    web 的 `Session.open` 用 `forkIn(会话 scope)`。
- **代价**:客户端必须自己启动引擎;中断一个"还没开始执行"的引擎不会触发清理,
  已排队的 `ask` 可能挂住(测试里用 `Effect.yieldNow` 先让它跑起来)。见
  [`../decisions/0010-run-is-the-loop.md`](../decisions/0010-run-is-the-loop.md)。
- **验证**:新增"引擎停止后 ask 立即失败"用例;`pnpm check` / `typecheck` / `test`(6 文件 56 用例)/ `build` 全绿。
- **落档**:重写 [`../designs/agent/loop.md`](../designs/agent/loop.md),`0009` 标注接口部分被
  [`0010`](../decisions/0010-run-is-the-loop.md) 取代。

## system prompt 砍到最简

- **为什么**:工具的名字 / 描述 / 参数已经在请求的 `tools` 字段里,提示词再列一遍是第二份事实;
  人格与"先查后答 / 简洁结论"属于软约束,不该硬编码在内核。
- **怎么改**:`systemPromptFor(toolNames)` → `systemPromptFor(hasTools)`:
  - 有工具:只留一句"不要执行破坏性命令";
  - 没工具:保留"本次没有任何工具可用 + 禁止输出 `<tool_call>` / 声称执行过命令";
  - 删掉 `PERSONA`、工具名枚举、行为提示。
- **保留的例外**:空工具的否认是实测 bug 的修复(否则模型把调用写成正文),不是重复。
- **验证**:新增断言"有工具时 system 不含 `bash`、而 `llm.complete` 的 `tools` 里有 `bash`";
  `pnpm check` / `typecheck` / `test`(6 文件 56 用例)/ `build` 全绿。
  真 key 冒烟:最简提示词下仍正常调 `list_dir` / `find`(参数错还会自我纠正),两轮答案正确 ——
  说明工具名字列表不是模型感知工具的必要条件。
- **落档**:[`../decisions/0011-minimal-system-prompt.md`](../decisions/0011-minimal-system-prompt.md)。

## 去掉 `MAX_STEPS`

- **为什么**:12 步兜底会截断合法长任务,而且返回的是内核伪造的"(已达到最大步数…)"——
  `ask` 的调用方会把它当答案,transcript 里却没有对应 assistant。
- **怎么改**:删 `MAX_STEPS`、`Turn.steps` 和上限分支;循环只在"模型只回正文"或"引擎被中断"时停。
- **代价**:模型可能一直调工具,烧 token 且 `ask` 不返回;没有自动兜底。见
  [`../decisions/0012-no-step-limit.md`](../decisions/0012-no-step-limit.md)。
- **验证**:原"最大步数兜底"用例改成"20 轮工具调用后仍拿到最终回答";
  `pnpm check` / `typecheck` / `test`(6 文件 56 用例)/ `build` 全绿。

## Agent 封装 inbox

- **为什么**:0010 把 `Inbox` 暴露给客户端后,外部要同时拿 `Agent` 和 `Inbox`、自己配对
  "起引擎 / 塞消息";inbox 是内部交接面,不该出现在 SDK 上。
- **怎么改**:`AgentShape` 增加 `ask`(内部转发 `inbox.ask`);`AgentLive` 改用 `Layer.provide(InboxLive)`,
  输出只有 `Agent`;SDK 不再导出 `Inbox` / `InboxShape` / `InboxMessage`;客户端统一 `agent.ask(...)`。
  `run` 仍是无限循环,生命周期约定不变。
- **代价**:Agent 同时承担"引擎 + 请求-应答";事件仍只发给当次 `ask` 的 `observe`,
  没有全局订阅。见 [`../decisions/0013-agent-encapsulates-inbox.md`](../decisions/0013-agent-encapsulates-inbox.md)。
- **验证**:`pnpm check` / `typecheck` / `test`(6 文件 56 用例)/ `build` 全绿。

## prompt 纯化 + 生命周期事件;ask 移出 Agent

- **为什么**:0013 的 `Agent.ask` 把"怎么等一轮回答"烘进内核;`PromptMessage` 还带着
  settings / tools / observe / reply,消息不纯;事件只有扁平的 thinking / text / tool_*。
- **怎么改**:
  - `Agent` 对外变成 `configure` / `send` / `events` / `run`;`ask` 删除,由客户端订阅
    `turn.end` 实现(CLI / REPL 各一份 `_turn.ts`,web 是流式变体);
  - `PromptMessage` 只剩 `{ id, text }`;settings / tools 通过 `configure` 写进内部 `Ref`;
  - `AgentEvent` 改成层级:`engine.start → turn.start → step.start → llm.start … llm.end →
    tool.batch.start → tool.call.start/end → tool.batch.end → step.end → turn.end → engine.end`;
  - `Inbox` 退回纯队列;中断时 `onExit` 补齐未关闭的 step / turn / engine.end;
  - web UI 按 `tool.call.start/end` 的 `callId` 回填块,忽略 lifecycle 事件。
- **代价**:`ask` 在客户端重复实现;事件是热流(先订阅再 send);配置是 Agent 级,
  中途 configure 在下一次生成生效。见
  [`../decisions/0014-agent-events-and-config.md`](../decisions/0014-agent-events-and-config.md)。
- **验证**:`pnpm check` / `typecheck` / `test`(6 文件 56 用例)/ `build` 全绿。

## `prompt.received`:事件流带 prompt 原文

- **问题**:`turn.start` / `turn.end` 只有 `promptIds`,事件流里拿不到 prompt 内容;
  当前客户端各自知道自己发了什么,但 UI / 重放 / archive 无法从事件还原用户消息。
- **怎么改**:新增顶层事件 `prompt.received { promptId, text }`,由 `Agent.send` 在入队前发出;
  `turn.start` / `turn.end` 继续只带 id,避免同一段文本重复。
- **验证**:新增用例断言 `prompt.received` 带原文、`turn.start.promptIds` 引用同一个 id;
  `pnpm check` / `typecheck` / `test`(6 文件 57 用例)/ `build` 全绿。

## 事件分结构 / 内容,补 `inbox.offer` / `inbox.take`

- **为什么**:0014 的事件里 `turn.end.answer`、`tool.call.*.arguments/output`、`llm.end.error`
  都是"结构事件夹内容";而且只有消息到达、没有出队,无法还原 inbox。
- **怎么改**:
  - 结构事件只带 id / 阶段:`inbox.offer/take`、`turn.start/end`、`step.*`、`llm.start/end`、
    `tool.batch.*`、`tool.call.start/end`;
  - 内容独立:`prompt.received`、`thinking` / `text` / `answer`、`llm.error` / `turn.error`、
    `tool.call.arguments` / `tool.call.output`;
  - `Agent.send` = prompt.received → inbox.offer → 入队;executor = tool.call.output → inbox.offer → 入队;
    状态机每次 `takeAll` 发 `inbox.take`;
  - 客户端 `runTurn` / web `Session.turn` 改为收集 `answer` / error 内容,到 `turn.end` 收尾。
- **代价**:事件条数变多;客户端要缓冲内容;`inbox.take` 是出队而非已处理。见
  [`../decisions/0015-event-content-structure.md`](../decisions/0015-event-content-structure.md)。
- **验证**:新增"inbox.offer − inbox.take = 未取走消息"与"turn 结束 inbox 为空"两条用例;
  `pnpm check` / `typecheck` / `test`(6 文件 59 用例)/ `build` 全绿。

## 扁平事件:`inbox.offer` 带内容,删掉 llm / tool 生命周期

- **为什么**:0015 的 `prompt.received` / `tool.call.arguments` / `tool.call.output` 让 inbox 内容与
  offer 分离;`llm.start/end`、`tool.batch.*`、`tool.call.start/end` 没有状态价值,只是噪声。
- **怎么改**:
  - `inbox.offer { message }` 成为内容事件,message 是完整 prompt / tool_result;
  - step 只含 `thinking` / `text` / `tool.call`;工具结果作为 `inbox.offer` 回来;
  - 最终答复是 turn 级的 `answer.produced`;错误只留 `turn.error`;
  - 删掉 `prompt.received`、`llm.*`、`tool.batch.*`、`tool.call.start/end`、`tool.call.arguments/output`。
- **代价**:`inbox.offer` 是"内容 + 入队"的有意例外;没有工具 / LLM 级时间线。见
  [`../decisions/0016-flat-events.md`](../decisions/0016-flat-events.md)。
- **验证**:`pnpm check` / `typecheck` / `test`(6 文件 59 用例)/ `build` 全绿。

## 去掉 `answer.produced`:回答由外部从 step 内容判断

- **为什么**:`answer` 是"这段 text 是不是最终回答"的解释,不是事实;内核不该替客户端判断。
- **怎么改**:
  - 删掉 `answer.produced`;`text` 就是 step 内模型产出的正文;
  - 外部折叠:每步 `step.start` 清空缓冲,`text` 追加,`turn.end` 时缓冲区就是最后一步的正文;
  - CLI / REPL 渲染器缓冲 text,遇到 tool.call 才作为"宣告"打印;最后一步由 `runTurn` 统一打印;
  - web 宿主缓冲每步 text,工具步的宣告照常转发,最后一步的 text 由终止行 `answer` 替代。
- **代价**:每个客户端都要实现同一段折叠;渲染容易重复。见
  [`../decisions/0017-answer-is-external.md`](../decisions/0017-answer-is-external.md)。
- **验证**:`pnpm check` / `typecheck` / `test`(6 文件 59 用例)/ `build` 全绿。

## `inbox.take` 也带完整消息

- **为什么**:`take` 只有 id 时不自信,回放 / 审计要回到 `offer` 查内容;offer 被裁剪后 take 就失去内容。
- **怎么改**:`inbox.take { messages }` 直接带出队的完整 prompt / tool_result;
  inbox 投影仍按 id 做差,但两边都自带内容。
- **代价**:同一条消息在 offer / take 各出现一次,archive 体积多一份;redact 要覆盖两处。见
  [`../decisions/0018-inbox-take-content.md`](../decisions/0018-inbox-take-content.md)。
- **验证**:`pnpm check` / `typecheck` / `test`(6 文件 59 用例)/ `build` 全绿。

## 澄清结构 / 内容:`inbox.take` 回到引用

- **纠正**:`inbox.take` 属于**内容**类事件(它不是 start/end 生命周期),但只带 `messageIds`;
  消息正文已经在 `inbox.offer`,不复制。
- **结构 / 内容判据**:
  - 结构 = `engine.*` / `turn.*` / `step.*` 的 start…end,生命周期容器;
  - 内容 = 容器里发生的事:`inbox.offer`(完整消息)、`inbox.take`(引用)、`thinking` / `text` /
    `tool.call`、`turn.error`。
- **代价**:take 不自信,回放要 join offer;好处是不重复、不双份 redact。
- **落档**:[`../decisions/0019-lifecycle-vs-content.md`](../decisions/0019-lifecycle-vs-content.md)。

## promptIds 下放到 step

- **为什么**:`turn.start/end` 带 `promptIds` 是让生命周期结构承载内容;而且等工具时合并进来的
  prompt 只能体现在 `turn.end`,看不出属于哪一步。
- **怎么改**:
  - `turn.start { turnId }` / `turn.end { turnId, reason }` 去掉 `promptIds`;
  - 新增 step 内容事件 `prompt { turnId, step, promptIds }`,只在这一步有新 prompt 时发;
  - `turn.error { turnId, promptIds, message }` 供"还没进 step 就失败"时认领;
  - 客户端改为:看到 `prompt` / `turn.error` 含自己的 id 时记下 turnId,再等这一 turnId 的 `turn.end`。
- **代价**:关联多一步;空 step 没有 prompt 事件。见
  [`../decisions/0020-prompt-ids-in-step.md`](../decisions/0020-prompt-ids-in-step.md)。
- **验证**:`pnpm check` / `typecheck` / `test`(6 文件 59 用例)/ `build` 全绿。

## 层级统一为 `id` / `parentId`

- **为什么**:`turnId` / `stepId` / `step` 每层一套字段,内容事件还要知道最近两层 id;结构信息散在 payload。
- **怎么改**:所有事件共用 `{ id, parentId? }`;start/end 共用同一个 id;
  turn 的 parent 是 engine,step 的 parent 是 turn,step 内容的 parent 是 step;
  删除 `turnId` / `step`;`promptIds` 仍只在 step 的 `prompt` / `turn.error` 里。
- **代价**:客户端要存 `stepId → turnId` 映射;内容事件也多一个 id。见
  [`../decisions/0021-id-parent-id.md`](../decisions/0021-id-parent-id.md)。
- **验证**:`pnpm check` / `typecheck` / `test`(6 文件 59 用例)/ `build` 全绿。

## 错误按层级拆分:step.error / turn.error / engine.error

- **为什么**:模型调用失败是 step 级,没配置是 turn 级,引擎缺陷之前没有对应事件。
- **怎么改**:
  - `step.error { parentId: stepId, message }` ← `llm.complete` 的 `LlmError`;
  - `turn.error { parentId: turnId, promptIds, message }` 保留给 turn 级失败(如没配置);
  - `engine.error { parentId: engineId, message }` 由 `onExit` 在缺陷 / 未捕获错误时发;
  - 纯中断不发 error,只发 `engine.end(reason=interrupted)`。
- **代价**:客户端要处理三级错误;缺陷时同一件事会在 step/turn/engine 三层有不同表达。见
  [`../decisions/0022-error-levels.md`](../decisions/0022-error-levels.md)。
- **验证**:新增 `step.error` 断言与"引擎缺陷发 engine.error"用例;
  `pnpm check` / `typecheck` / `test`(6 文件 60 用例)/ `build` 全绿。

## 错误并入生命周期,统一格式

- **为什么**:`turn.error` 还在内容组且多带 `promptIds`,和 `step.error` / `engine.error` 不一致。
- **怎么改**:
  - 三级错误都放进生命周期组:`engine.start/error/end`、`turn.start/error/end`、`step.start/error/end`;
  - 格式统一为 `{ id, parentId, message }`;`turn.error` 去掉 `promptIds`;
  - 客户端改为用 `inbox.take` + `turn.start` 把 prompt 对齐到 turn,再看 `turn.error.parentId`。
- **代价**:认领逻辑更复杂;错误不再自带 prompt 列表。见
  [`../decisions/0023-errors-in-lifecycle.md`](../decisions/0023-errors-in-lifecycle.md)。
- **验证**:`pnpm check` / `typecheck` / `test`(6 文件 60 用例)/ `build` 全绿。

## `end` / `error` 互斥,错误带 kind

- **为什么**:`end.reason=error` 让正常结束事件也声明错误;错误没有分类;同一件事在 error/end 两处表达。
- **怎么改**:
  - `start → end` = 正常结束,`start → error` = 异常结束,错误后不再发对应 end;
  - `engine.end` / `turn.end` / `step.end` 去掉 `reason`;
  - `engine.error` / `turn.error` / `step.error` 统一 `{ id, parentId, kind, message }`,
    `kind ∈ llm | config | defect`;
  - 中断按正常停止处理(逐层 end,无 error);
  - 客户端不再判断 end.reason:end = 成功,error = 失败。
- **代价**:end 不再区分正常完成 / 用户中断;缺陷时三层 error 重复同一条 message。见
  [`../decisions/0024-end-or-error.md`](../decisions/0024-end-or-error.md)。
- **验证**:`pnpm check` / `typecheck` / `test`(6 文件 61 用例)/ `build` 全绿。

## error 回到内容,生命周期只有 start → end

- **为什么**:0024 让 error 替代 end,生命周期变成二选一;但 error 是"发生了什么"的内容,
  end 才是结构闭合。且 `kind` 属于内容字段。
- **怎么改**:
  - 生命周期只有 `engine/turn/step.start → end`;
  - `engine.error / turn.error / step.error` 回到内容组,去掉 `kind`,只留 `{id,parentId,message}`;
  - 出错后照常发所属层级的 end:模型失败 step.error→step.end→turn.error→turn.end;
    没配置 turn.error→turn.end;缺陷逐层 error 后逐层 end;
  - 客户端始终等 `turn.end` 收尾,失败信息从 error 内容取。
- **代价**:end 不表达成功/失败;error 与 end 都发;缺陷时三层 error 重复。见
  [`../decisions/0025-error-as-content.md`](../decisions/0025-error-as-content.md)。
- **验证**:`pnpm check` / `typecheck` / `test`(6 文件 61 用例)/ `build` 全绿。

## `_tag` 全大写,step 内容与 Item 对齐

- **为什么**:事件 tag 小写带点号,Item 用 `message + role`,step 内容又叫 `prompt/thinking/text/tool.call`;
  同一套语义四套名字。
- **怎么改**:
  - 所有 `_tag` 大写(`ENGINE_START` / `TURN_END` / `INBOX_OFFER` / …);
  - `Item` 拆成 `SYSTEM_MESSAGE` / `USER_MESSAGE` / `ASSISTANT_MESSAGE` / `REASONING` /
    `FUNCTION_CALL` / `FUNCTION_CALL_OUTPUT`;
  - step 内容事件与 Item 同名:`SYSTEM_MESSAGE` / `USER_MESSAGE`(promptIds)/
    `FUNCTION_CALL_OUTPUT` / `REASONING` / `ASSISTANT_MESSAGE` / `FUNCTION_CALL`;
  - inbox 消息改为 `USER_MESSAGE` / `FUNCTION_CALL_OUTPUT`;
  - web 终止行改为 `ANSWER` / `ERROR`;`LLM_ERROR` / `TOOL_INPUT_ERROR` 同步大写。
- **代价**:全量重命名;旧日志/旧决策名字不再匹配;step 内容与 inbox 有重复。见
  [`../decisions/0026-uppercase-tags-items.md`](../decisions/0026-uppercase-tags-items.md)。
- **验证**:`pnpm check` / `typecheck` / `test`(6 文件 61 用例)/ `build` 全绿。

## step 输入事件顺序:SYSTEM → USER → FUNCTION_CALL_OUTPUT,错误最后

- **为什么**:三者都是 LLM 输入,应同层;错误是结局,应放最后。
- **怎么改**:事件顺序改为 SYSTEM_MESSAGE → USER_MESSAGE → FUNCTION_CALL_OUTPUT →

## archive worker 改成 `forever(takeBetween >>= writeBatch)`

## 把关闭收尾里的 drain 提出来命名

  `关闸 → drain → 非空才写`。注释里写明:将来要显式 `flush`,就是 `drain` + `cachedSink.write`。
- **原因**:之前这段逻辑埋在 finalizer 的 gen 里,读不出"这是在收拢未落盘的条目";命名后
  `takeBatch` / `writeBatch` / `drain` 三个动词把 worker 的生命周期说完了。

## `drain` / `takeBatch` 改成动作(函数)

- **怎么改**:两个都从 `const x: Effect<…>` 改成 `const x = (): Effect<…>` 并在调用处写 `drain()`
  / `takeBatch()`;文档同步。
- **原因**:它们是"做一次"的动作,不是可以反复 yield 的固定值;写成函数让"每次调用收一次"
  这件事在类型和调用点都看得见。服务形状里的字段(`ArchiveShape.readAll`、`cachedSink.read`、

## `drain` 收回成 Effect 值,并把"关闸 + 写掉"并进去

- **怎么改**:`takeBatch` / `drain` 改回 Effect 值(上一版改成函数是误读);`drain` 不再是
  "只收拢",而是关闭收尾的**唯一动作**:关闸(`closed = true`)→ 收拢在飞批 + 队列残余(同一事务)
  → 非空就写进 sink。`onInterrupt` 因此缩成 `() => drain.pipe(Effect.ignore)`。
- **原因**:关闸必须先于收拢(否则收拢之后又进来的 `append` 永远没人写),写完才算"历史完整"——
  这三步本来就是一件事,分开放反而看不出是一体的。
- **代价**:`drain` 会关闸,不能当 `flush` 用;将来要显式 flush,得另写"只收拢 + 写"的动作。

## `loop/inbox.ts` 的 `settled` 改成模式匹配

- **怎么改**:`if (awaiting.length > 0)` 换成 `Arr.match(awaiting, { onEmpty, onNonEmpty })`;
  两个分支里的 `x.length > 0 ? some : none` 也换成 `Arr.match(..., { onEmpty, onNonEmpty })`。
  就位判断本身用集合差:`Arr.difference(等的 callId, 已回来的 callId)` 为空 = 齐了
  (`Arr.difference` 内部走哈希桶,O(n+m),比 `every` + `some` 的 O(n·m) 好读也好算);
  "已回来的 callId" 提成 `resultCallIds(messages)`。
- **原因**:这里的三个分叉本质都是"空 / 非空",模式匹配让"空"这一支显式列出来,不用在
  `length > 0` 与三元里反推。
- **验证**:`pnpm check` / `test`(10 文件 86 用例)/ `build` 全绿。

- **顺带记一笔**:v4 的 `Arr.filterMap` 要 `Result`(不是 `Option`),所以"Option 算子 + 收拢"

## `takeReady` 的等待逻辑改成模式匹配 + 递归

- **怎么改**:`while (true) { settled() ? 交出 : 再取 }` 换成 `Option.match(settled(...), { onSome, onNone })`:
  `onSome` = 清空攒着的并交出;`onNone` = 取一批(空则挂起)、攒进 `pending`、再判一次(递归)。
  「等待」这个循环由递归表达,不再手写 `while`。
- **原因**:`settled` 本来就返回 `Option`,两个分支正好是 match 的两种情形;少一层
  `isSome` + `break/return` 的跳转。
- **验证**:`pnpm check` / `test`(10 文件 86 用例,重跑三次稳定)/ `build` 全绿。

## `takeReady` 里取 `pending` 改成 `Effect.Do.pipe`

- **怎么改**:`Ref.get(pending).pipe(Effect.flatMap(wait))` 换成
  `Effect.Do.pipe(Effect.bind("messages", () => Ref.get(pending)), Effect.flatMap(({ messages }) => wait(messages)))`。
- **原因**:"读 pending → 用它"是一条链,do 记法把中间值命名成 `messages`,不用为一次读取
  再包一层 `Effect.gen` / 匿名参数。
- **验证**:`pnpm check` / `test`(10 文件 86 用例,重跑三次稳定)/ `build` 全绿。

## `takeReady` 去掉内部 `wait`,直接递归自己

- **怎么改**:嵌套的 `wait(messages)` 删掉,`takeReady` 本身就是一个 `Effect.Do.pipe`
  (`bind("messages", Ref.get(pending))` → `Option.match(settled(...))`);`onNone` 里存好新一批后
  `Effect.andThen(takeReady(awaiting))` 递归,"等待"就是它自己再跑一遍。
- **原因**:`wait` 只是把同一个动作换个名字,递归入口和对外入口没必要是两个人。
- **验证**:`pnpm check` / `test`(10 文件 86 用例,重跑三次稳定)/ `build` 全绿。

## `takeReady` 的 onSome 改成 `succeed(ready).pipe(tap(清空))`

- **怎么改**:`Ref.set(pending, []).pipe(Effect.as(ready))` 换成
  `Effect.succeed(ready).pipe(Effect.tap(() => Ref.set(pending, [])))`。
- **原因**:主体是"交出这一批",清空是附带动作 —— `tap` 让读的顺序与意图一致
  (结果在前、副作用挂上去),`as` 则读成"先清再返回",主次倒了。
  注意 `ready` 是值(不是 Effect),所以要先 `Effect.succeed` 再 `pipe`。
- **验证**:`pnpm check` / `test`(10 文件 86 用例,重跑三次稳定)/ `build` 全绿。

## `inbox.ts` 的 `offer` 也提到外面

## 输入并进 transcript 归到 3.3(调模型)里

## 确认:缓存必须在 sink 之后补,顺序不能反

- **结论**:不调整 —— `cachedSink.write` 保持"先 `sink.write`(含重试)成功,再补缓存"。
- **原因**:缓存是"已落盘条目的视图",`readAll` / `restore` 的契约是"只读已落盘"。
  如果先补缓存再写盘:写失败(重试耗尽)时 `readAll` 会报出根本没落盘的条目;中断也会在缓存里
  留下幽灵行,而文件里没有。
- **并发上不吃亏**:读与写在同一把 `Semaphore(1)` 里,所以"写盘了但缓存还没补"这个窗口对外不可见,
  不存在读到陈旧缓存的情况;唯一代价是"写成功后、补缓存前被中断"会少补最后一批 ——
  此时 sink 有、缓存没有,下次新建实例重读即可。
- **文档**:给 `cachedSink.write` 加了这段顺序说明(缓存不能领先于落盘)。
- **验证**:`pnpm check` / `test`(10 文件 89 用例)/ `build` 全绿。

## 缓存前移到写队列之前;engine 改成从 archive 投影 transcript

## 逐条折叠改用 `Effect.forEach`,去掉 `for`

- **怎么改**:`fold` 里不再 `for (const entry of incoming)` 就地遍历,改成
  `foldEntry(entry): Effect<void>`(一条条目 → 一次 `Ref.update`)+
  `Effect.forEach(incoming, foldEntry, { discard: true })`;空队列时 `forEach` 天然是空操作,
  所以连"没有待折就提前返回"的分支也省了。
- **原因**:折叠是"对每条条目做一件事",用 effect 的组合子表达比手写循环更直白;
  也让 `foldEntry` 成为可单独指认的一步(一条条目怎么改状态)。
- **代价**:每条条目一次 `Ref.update`(之前是整批一次)。Ref 更新本身很轻,而且整段仍在
  `Semaphore(1)` + `uninterruptible` 里,原子性不变;代价是单次折叠多了 N-1 次回调开销。
- **验证**:`pnpm check` / `test`(10 文件 89 用例,重跑三次稳定)/ `build` 全绿;`project.ts` 223 行。

## 待折队列改成 `Ref.modify` 原子取走,去掉 `slice`

- **怎么改**:`Ref.get` + 折完 `slice(incoming.length)` 换成一次
  `Ref.modify(incomingRef, (current) => [current, []])` —— 取走全部并清空是同一个原子操作。
- **为什么原来要 `slice`**:`advance` 不拿锁,折叠期间可能往 `incomingRef` 追加新条目;
  `slice(长度)` 是为了只清掉"我这一批"。但先 `Ref.set([])` 就会把这些新条目一起丢掉。
- **为什么 `modify` 更好**:同一个原子操作里完成"取走 + 清空",既不丢并发追加,也不用靠长度推算;
  折叠本身在 `Semaphore(1)` + `uninterruptible` 里跑,取走之后不会被中断丢条目。
- **验证**:`pnpm check` / `test`(10 文件 89 用例,重跑三次稳定)/ `build` 全绿。

## "取走 → 折 → 清空"三步,`advance` 也拿同一把锁

- **怎么改**:`Ref.modify` 换成 `Ref.get` → `Effect.forEach(incoming, foldEntry)` → `Ref.set(incomingRef, [])`;
  同时 `advance` 入队也走同一把 `Semaphore(1)`。
- **原因**:`modify` 的 `[值, 新状态]` 元组读起来不直观;三步写法是直白的"取、折、清空"。
  但这三步之间不是原子的,所以把 `advance` 也纳入锁 —— 否则中间追加的条目会被 `set([])` 一起清掉。
- **代价**:入队要等折叠结束(折叠是纯内存、通常几条到几十条,影响很小);
  反过来也意味着读者和写者共用一把锁,不再是读写分离。
- **验证**:`pnpm check` / `test`(10 文件 89 用例,重跑三次稳定)/ `build` 全绿。

## `SynchronizedRef`:状态与待折队列收进一个 Ref,去掉手写锁

- **起因**:`Ref.update` 的回调必须是纯同步函数(`f: (a) => a`),里面不能 `yield*`。
  但 Effect 有 effectful 版本:`SynchronizedRef.updateEffect` / `modifyEffect`(内部自带一把
  semaphore,只有 effect 成功才提交新值)。
- **怎么改**:`stateRef`(`FoldState`)、`incomingRef`、`lock` 三样合成一个
  `SynchronizedRef<{ folded, incoming }>`:
  - `advance` = `SynchronizedRef.update`(纯,folding 期间排队);
  - `fold` = `SynchronizedRef.modifyEffect`:取走 `incoming` → `Effect.forEach(foldEntry)` →
    返回 `[folded, { folded, incoming: [] }]`,取走/折/清空是一次原子提交;
  - 手写的 `Semaphore` 与"三步之间加锁"的注释整段删掉。
- **代价**:`SynchronizedRef` 每次操作都过一次 semaphore(比 `Ref` 重);状态对象里多了 `incoming` 字段
  (队列与折叠状态绑在一起,语义上略有混搭)。折叠仍要 `Effect.uninterruptible`:就地改过的状态
  一旦被打断,会和没清空的 `incoming` 对不上。
- **验证**:`pnpm check` / `test`(10 文件 89 用例,重跑三次稳定)/ `build` 全绿;`project.ts` 219 行。

## `modifyEffect` 的返回值形状写清楚

## 投影状态拆成 5 个 Ref:`queue` / `staged` / `transcript` / `step` / `incoming`

  否则"清空"之后插进来的条目会被 `Ref.set([])` 丢掉。
- **连带好处**:更新都改成不可变写法(数组整份替换),读侧不再需要拷贝 —— `get` 直接

## `fold` 写成直接的 `Effect.gen`

- **怎么改**:`SynchronizedRef.modifyEffect` + 元组返回那套删掉,换成
  `lock.withPermit(uninterruptible(gen { get → set([]) → forEach 折 }))`;`incomingRef` 退回普通 `Ref`。
- **原因**:元组 `[返回给调用方的值, 新状态]` 读起来绕;"清空队列"就是一句话,不需要额外语义。
- **代价**:因为 `get` 和 `set` 之间不是原子的,`advance` 也得拿同一把锁(否则中间追加的条目被清掉);
  锁的持有范围从"读者"扩到"读者 + 写者"。
- **验证**:`pnpm check` / `test`(10 文件 89 用例,重跑三次稳定)/ `build` 全绿。

## 去掉 `fold` 的 `Effect.uninterruptible`

- **怎么改**:`lock.withPermit(Effect.uninterruptible(gen { … }))` → `lock.withPermit(gen { … })`,
  并在注释里写明依赖的前提:整段只有同步的 `Ref` 操作。
- **能去掉的原因**:中断只在异步边界(或显式 `yieldNow`)上生效;这里全是 `Effect.sync` 系
  (`Ref.get` / `Ref.set` / `Ref.update`),`Effect.forEach` 串的也是同步操作,插不进来。
- **代价**:安全性从"由库保证"变成"由这里没有异步步骤保证"。如果 `foldEntry` 以后引入异步步骤
  (比如中途读文件),中断就可能停在"队列已清空、条目没折完"的位置 —— 那时要重新加回
  `uninterruptible`,或改成先折后清 + 去重。注释里写了这条复查条件。
- **验证**:`pnpm check` / `test`(10 文件 89 用例,重跑三次稳定)/ `build` 全绿。

## 用 STM(`Effect.tx` + `TxRef`)替掉 `Semaphore` / `uninterruptible`

- **起因**:确认 `Effect.tx` 的事务是"日志 + 提交":写先记在 journal 里,只有事务成功且
  `isTransactionConsistent` 才提交;中断 / 失败会 `clearTransaction` 丢掉日志 —— 也就是回退。
  它同时解决三件事:多 Ref 原子性、并发冲突(版本不一致就整段重跑)、中断安全。
- **怎么改**:5 个状态从 `Ref` 换成 `TxRef`;`fold` = `gen { 取走并清空 → forEach foldEntry }.pipe(Effect.tx)`;
  `advance` = `Effect.tx(TxRef.update(...))`;`get` 的读取也包进一个事务(否则可能读到
  "折了一半"的两个快照)。`Semaphore` 与 `uninterruptible` 都不再需要。
- **代价**:所有状态操作必须是 `TxRef`(`Ref` 不参与 journal);冲突时整段重跑(这里折叠是纯内存,重跑代价小);
  `TxRef.modify` 要求**可变**元组(`[值, 新值]`),`removeById` 的返回类型由此从 `readonly` 改成可变。
- **复查条件**:若折叠要把结果写到 STM 之外(文件 / 队列),事务回退就不再覆盖那部分,需要重新评估。
- **验证**:`pnpm check` / `test`(10 文件 89 用例,重跑三次稳定)/ `build` 全绿;`project.ts` 260 行。

## `foldEntry` 从 `switch` 改成 `Match`

- **怎么改**:`switch (entry._tag)` 换成 `Match.value(entry).pipe(Match.when({ _tag: ... }, …), Match.orElse(…))`,
  每个分支上方一句注释说清它做什么;不再需要"编译器不当成可穷尽判别"的兜底 `return`。
- **原因**:与仓库其它地方(`inbox.ts` 的 `readyBatch` / `takeReady`)统一;`Match.orElse` 天生吃掉
  不进投影的那些 tag(`TURN_*` / `*_ERROR` / `SYSTEM_MESSAGE_*` / `ARCHIVE_ERROR`),比列一串空 case 干净。
- **验证**:`Match.when({ _tag: "X" }, e => …)` 对 `ArchiveEntry`(条件类型联合)能正确窄化 payload;
  `pnpm check` / `test`(10 文件 89 用例,重跑三次稳定)/ `build` 全绿;`project.ts` 253 行。

## `get` 摊平成一个 `gen`

- **怎么改**:`fold.pipe(Effect.andThen(() => gen{…}.pipe(Effect.tx)))` 换成
  `gen { yield* fold; if (transcript) …; 读 queue/staged }.pipe(Effect.tx)`。
- **原因**:三层嵌套(`pipe` / `andThen` / `gen`)只为了表达"折完再读",摊平后一眼看到顺序。
  顺带把读也放进同一个事务:`fold` 内部那个 `Effect.tx` 在事务里是空操作,所以"折 + 读"整体原子,
  比"折完出来再单独开事务读"更严格。
- **验证**:`pnpm check` / `test`(10 文件 89 用例,重跑三次稳定)/ `build` 全绿;`project.ts` 249 行。

## 去掉 `get` 尾部的 `as ProjectionShape["get"]`

- **起因**:那个 cast 是为了把"接收 `keyof Projections`、返回联合类型"的实现硬塞给泛型签名
  `<K>(kind: K) => Effect<Projections[K]>` —— 它丢掉了 kind 与返回值的对应关系,是类型漏洞。
- **怎么改**:加一张 `readers` 表(`{ [K in keyof Projections]: () => Effect<Projections[K]> }`),
  `get` 写成真正的泛型:`<K extends keyof Projections>(kind: K) => gen { yield* fold; return yield* readers[kind]() }.pipe(Effect.tx)`,
  `readers[kind]` 在 `kind: K` 下就是 `Effect<Projections[K]>`,不需要任何 cast。
- **顺带**:类的"二选一"变成查表,加第三类投影只是加一行(0078 里记的"以后要改成 switch 或表"提前做了)。
- **验证**:`pnpm check` / `test`(10 文件 89 用例,重跑三次稳定)/ `build` 全绿;`project.ts` 256 行。

## `readers` 表留在服务作用域(内联会丢类型);顺手去掉 `archive.ts` 的同款 cast

- **试过内联**:把 `readers` 搬进 `get` 的 gen,`readers[kind]` 的类型退化成
  `Effect<readonly Item[] | InboxProjection>`,赋给 `Effect<Projections[K]>` 报错 —— 要过就得再加 `as`,
  等于把刚去掉的漏洞请回来。内联版还会每次调用重建一次表。所以留在服务作用域,一次构建。
- **顺手**:`archive.ts` 里 `projection: ((kind) => projection.get(kind)) as ArchiveShape["projection"]`
  也有同样的 cast;写成泛型箭头 `<K extends keyof Projections>(kind: K) => projection.get(kind)` 就不需要了。
- **验证**:`pnpm check` / `test`(10 文件 89 用例,重跑三次稳定)/ `build` 全绿。

## `readers` 表删掉,`get` 内联 + 一处 `as`

- **怎么改**:去掉映射类型表,`get` 里直接按 `kind` 二选一读,值先落到
  `Projections[keyof Projections]`,再 `as Projections[K]` 交回泛型签名。
- **理由**:表只为了"让编译器自己推出对应关系";既然接受一处 `as`,表就是多余的一层。
  cast 收在返回值这一行,旁边写清"对应关系由分支保证",比 cast 整个函数(`as ProjectionShape["get"]`)更局部。
- **代价**:这里的类型安全靠约定 —— 加第三类投影时若忘了加分支,编译器不会提醒。
- **验证**:`pnpm check` / `test`(10 文件 89 用例,重跑三次稳定)/ `build` 全绿;`project.ts` 255 行。

## `get` 的 kind 分支改成 `Match` + `Match.exhaustive`

- **怎么改**:`kind === "transcript" ? … : …` 换成
  `Match.value(kind as keyof Projections).pipe(Match.when("transcript", …), Match.when("inbox", …), Match.exhaustive)`。
- **为什么要把 `kind` 放宽成 `keyof Projections`**:`Match.value(kind)`(K 是泛型)时,`"transcript"` 这类字面量
  不满足 `PatternPrimitive<K>`,编译不过。
- **好处**:`Match.exhaustive` 让"加了新投影却忘了写分支"变成**编译错误**(试过:删掉 inbox 分支立刻报错),
  补上了上一轮内联时丢掉的那层检查。
- **仍然需要一处 `as Projections[K]`**:`Match` 的结果在泛型 K 下还是联合类型,这条对应关系编译器推不出来。
- **验证**:`pnpm check` / `test`(10 文件 89 用例,重跑三次稳定)/ `build` 全绿;`project.ts` 260 行。

## `advance` / `get` 提到 `Projection.of` 外面单独定义

- **原因**:服务组装那几行只该回答"有哪两个能力",具体实现放在上面按顺序铺开
  (`fold` → `advance` → `get`),读代码不用在对象字面量里追实现。

## `advance` 改成分支明确的 `Match`

- **怎么改**:`entries.length === 0 ? Effect.void : 入队` 换成
  `Match.value(entries).pipe(Match.when(hasEntries, 入队), Match.orElse(空批次 → Effect.void))`,

## `advance` → `ingest` → 又改回 `advance`

- **语义问题**:`advance` 暗示"把折叠过程往前推",但它其实只做一件事——把这批条目收进待折队列;

## `run` 变成"起引擎 + 交出句柄",`events` 不再单独暴露

- **怎么改**:`LoopShape` 去掉 `events`,字段变成 `run: Effect.Effect<LoopRun>`:
  ```ts
  interface LoopRun {
    events: Stream<ArchiveEntry>;
    fiber: Fiber<never, never>;
  }
  ```
  实现:`const fiber = yield* engine.run.pipe(Effect.forkIn(layerScope, { startImmediately: false }));`
  → `return { events: events.stream, fiber }`。SDK 边界把 `LoopRun` 以 `AgentRun` 导出。

  - `forkIn(层的 scope)`:引擎跟**这一层**同生共死,不跟 `run` 这个 Eff果本身 —— 否则 `run` 一返回,
    它的子纤维就被回收了(web 宿主是 fork+join 的写法,会被直接掐掉);

- **代价**:不能再"先订阅 `Agent.events`、再起引擎"(事件流只在 `run` 之后才有);一次 `run` 只能拿一个句柄。

## `Match.value(yield* ...)`:值直接在 `value` 里取

- **怎么改**:`Ref.get(...).pipe(Effect.flatMap((x) => Match.value(x).pipe(...)))` 的多层嵌套,
  换成一行 `yield* Match.value(yield* Ref.get(ref)).pipe(...)`。
- **为什么**:`flatMap` 那一层只是为了把值递进 `Match`;`Match` 的分支本来就返回 Effect,
  直接 `yield*` 整个匹配结果即可,少一层缩进和一层 `current` 变量。
- **验证**:`pnpm check` / `test`(10 文件 90 用例,重跑三次稳定)/ `build` 全绿。

## `batches`:`flatMap` 换成 `Effect.gen`

- **怎么改**:
  ```ts
  Stream.fromEffectRepeat(
    Effect.gen(function* () {
      const pending = yield* Ref.get(pendingCallsRef);
      return yield* inbox.takeReady(pending.map((call) => call.callId));
    }),
  );
  ```
- **为什么**:原来 `.pipe(Effect.flatMap((calls) => ...))` 只是为了把 Ref 的值递进去;`gen` 里两行按顺序读下来,
  和"读在飞调用 → 等这批就位"同一句话。`fromEffectRepeat` 仍然是"每次 pull 才跑一遍",语义不变。
- **验证**:`pnpm check` / `test`(10 文件 90 用例,重跑三次稳定)/ `build` 全绿。

## `pendingCalls` 的清空挪到 `takeReady` 之后

- **怎么改**:`batches` 的 `Effect.gen` 里,`inbox.takeReady(...)` 返回后立刻 `Ref.set(pendingCallsRef, [])`;
  `handleBatch` 里那句 `yield* Ref.set(pendingCallsRef, [])`(3.3 调模型之前)删掉。
- **为什么**:"就位"这件事本身已经证明这些结果都回来了,清空的时机就是那一刻;
  把它写在 `handleBatch` 里等于"处理这一批时顺手清一下",读的人还得回头确认"为什么清"。
- **语义**:在飞清单的生命周期现在是 **"从派发 → 到这批就位"**,边界清楚;
  下一批的 `takeReady` 不会再等已经消费过的调用。
- **验证**:`pnpm check` / `test`(10 文件 90 用例,重跑三次稳定)/ `build` 全绿。

## 语义化命名:`takeReady` → `takeReadyBatch`,`pending` → `pendingCalls`,`batch` → `readyBatch`

- **怎么改**:
  - `InboxShape.takeReady` → `takeReadyBatch`(实现、递归调用、`Inbox.of({...})`、engine 调用点、测试);
  - `engine` 的 `batches` 里:`pending` → `pendingCalls`,`batch` → `readyBatch`;
  - `handleBatch` 的参数 `batch` → `readyBatch`。
- **为什么**:方法名说清"交出的是整批(`ReadyBatch`)",与返回类型同名;
  局部变量也带上"是什么"(在飞调用 / 就位的一批),而不是靠上下文猜 `batch` 指哪一批。
- **连带**:`docs/designs/agent/{inbox,loop}.md` 里出现的 `takeReady` 同步。
- **验证**:`pnpm check` / `test`(10 文件 90 用例,重跑三次稳定)/ `build` 全绿。

## `batch` 的单复数:一批用单数,数组用复数

- **规则**:"一批"是**一件事**(它内部才是数组)→ 单数;多批 → 复数(`batches` 那条流);
  数组本身 → 复数(`entries` / `calls` / `messageIds`)。
- **按规则改的**:`writeBatch(entries)`、`takeBatch` 里 `batch` → `entries`、`sink` 的 `write(entries)`;
  `memory` 的 `write(incoming)`(与本地 `entries` 区分);`executeBatch(toolBatch)` / `submit(toolBatch)`;
  `projection` 的 `Match.when(hasEntries, (entries) => …,)`;`isReady(candidate)`(它是"可能就位的那批",不是一批)。
- **没改**:`ReadyBatch` / `TakeReadyBatch` / `handleBatch` / `ToolBatch` / `batches` —— 单数指"一批",复数指"多批",
  已经符合这条规则。
- **验证**:`pnpm check` / `test`(10 文件 90 用例,重跑三次稳定)/ `build` 全绿。

## `batches` → `readyBatchStream`,`handleBatch` → `handleReadyBatch`

- **怎么改**:`run` 里的批次流改名 `readyBatchStream`(元素类型是 `ReadyBatch`),消费它的回调改名
  `handleReadyBatch`;「方法」段的标题跟着改。
- **为什么**:`batches` 只说明"复数",没说流里装的是什么;`handleBatch` 同样 —— 处理的是"就位的一批"。
  `Ready` 这个词和 `inbox.readyBatch` / `takeReadyBatch` 对齐,一眼能看出这条流的来源。

## 生命周期动作补齐成一对:`startStep`/`startTurn`/`endStep`/`endTurn`/`failStep`/`failTurn`

- **怎么改**:
  - `closeStep` → `endStep`、`finishTurn` → `endTurn`(行为不变);
  - 新增 `startTurn()`:在轮里就沿用,不在就开一条并 `TURN_START`;

## `startStep` 自己取 `turnId`

- **怎么改**:`startStep(turnId)` → `startStep()`,内部读 `turnIdRef`;`handleReadyBatch` 里 `startTurn()` 的返回值
  随之不再需要(`yield* startTurn();` 即可)。
- **为什么**:step 永远挂在"当前轮"下,轮 id 是状态而不是参数;传参等于把同一个事实说两遍,

## 页面空白的原因与修法:根入口被 Node 依赖污染

- **现象**:`localhost:5173` 白屏,Vite 控制台报

- **修法**:根入口保持**平台无关**:

## `send` 收进 `run` 的句柄

- **怎么改**:`LoopShape` 只剩 `configure` + `run`;`LoopRun` 变成 `{ events, fiber, send }`。
  `LoopLive` 的 `run` 把 `send` 一起交出去,`Loop.of({ configure, run })`。
- **为什么**:prompt 只该发给**已经跑起来的**引擎 —— 把 `send` 放进句柄,这个前提变成类型上的:
  拿不到句柄就没有"发 prompt"这回事,不用再靠"记得先 run"的约定。
- **调用点**:`runTurn(session, text, onEvent)`(repl / cli / smoke)、web 宿主的 `turn`、两个测试的 `ask(run, text)`
  都改成从句柄上 `send`;`AgentRun` 从包根导出。

## `configure` 也收进 `run` 的句柄

- **怎么改**:`LoopShape` 只剩 `run`;`LoopRun = { events, fiber, send, configure }`。
  调用点顺序改成"先 run 拿句柄,再 `run.configure(...)`,再 `send`":repl / cli / smoke / web 宿主 / 两个测试。
- **为什么**:`configure` / `send` / `events` 都只对**已经跑起来的引擎**有意义,把它们全挂在 `run` 的返回值上,

- **顺序为什么安全**:引擎以 `startImmediately: false` fork,且第一批发来之前不读配置
