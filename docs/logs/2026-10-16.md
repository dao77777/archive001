## 深挖 store / include / encrypted_content

- 起因:「`store` 和 `include` 到底干嘛的?状态存了什么?`encrypted_content` 还是不懂」。
- 拿到官方原话:`store` = _"Whether to store the generated model response for later retrieval via API."_(默认 true);
  `include` = "额外返回这些默认不返回的字段",官方列了 7 个取值 —— 关键那句是
  `reasoning.encrypted_content` 用于 **statelessly**(`store:false` 或 ZDR)时让 reasoning item 能跨轮使用。
- 拿到官方数据政策表:`/v1/responses` abuse 日志 30 天;ZDR 会**强制** `store=false`;
  API 数据自 2023-03-01 起不用于训练。`/v1/conversations` 是 `Until deleted`(更重)。
- 想通的因果链:那个 404 `Item with id 'rs_…' not found. Items are not persisted when store is set to false.`
  = 服务端**按 id 查自己的库**。store:true 查得到(不需要密文);store:false 查不到(必须自己带密文)。
  **一个 store 开关 + 一个 include 开关,解释了全部现象。**
- 由此得到一条架构结论并写进文档:本项目**只能**用 `store:false` ——
  因为我们自己在 `Ref` 管历史,而 DeepSeek/Anthropic 没有服务端状态;用 store:true 会让 openai
  成为唯一有状态的厂商、破坏统一形状。所以 `store:false + include` 是必然,不是随手配置。
- 文档:`../knowledge/responses-api-internals.md` 由 64 行扩到 142 行,补上「寄存行李的回执」类比与四组合表。

## 「主要目的其实是防蒸馏吧」——被怼了一次,改了文档

- 用户的批评站得住:**我把「官方动机陈述」当成了「机制解释」写**。动机陈述是自利的、且不可证伪 ——
  任何组织都能为对自己有利的决定找出无限多合理理由。这是我的方法论错误。
- 改法不是反过来说"就是防蒸馏"(那是同一种错误换方向),而是**把证据分级**:
  - **机制事实**(强):`store:false` 只需要一个状态载体,**加密是多余的** —— 它唯一多加的功能就是"你读不了"。
    所以「不让你读」可被**机制本身证明**是设计目标。
  - **但机制区分不了理由**:防蒸馏和防泄露需要**同一个东西**,所以"真正动机是哪个"**在证据上不可判定**。
  - **官方说法**(弱):有害内容 / 泄露 instructions。**不全是公关** —— 泄露 system prompt 对部署方是真实的边界穿透。
  - **防蒸馏**(有间接证据):OpenAI 公开指控 DeepSeek 蒸馏;import 用同门弱模型"念出"旗舰模型加密推理块的论文
    (推理块未严格绑定会话/用户/模型,存在跨会话·跨用户·跨模型互通)。
- 顺手否掉一个**伪反例**:拿 `gpt-oss`(开放权重给明文 CoT)证明"原则让步"不成立 ——
  开放权重本来也防不住蒸馏,给不给明文不改变结果。
- 由此得到一条**与本项目直接相关的安全约束**(写进 AGENTS.md 与知识文档):
  已在 GitHub/HF 的 6708 条公开轨迹中还原 31.5 万推理块,4.9% 泄露 API key / 密码 / 私钥。
  → **绝不持久化 `reasoning` / `reasoningSignature`**。核实过:`remember()` 里两者恒为 `null`,
  带推理的消息只活在单次 run 的局部变量里 —— 现状是对的,但已写成硬规矩防止回退。
