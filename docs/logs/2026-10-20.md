# 2026-10-20

## 把 otter 砍到只剩 DeepSeek

**起因**:项目只有 DeepSeek 的 key,真正跑的也只有 DeepSeek;三家的适配器每天在增加读代码的成本。
决定只留两条 wire(`/chat/completions` 与 `/responses`),并顺手把域模型里的 wire 残留清掉。

### 先做实测,再动代码

用 vault 里的 key 打 `deepseek-flash`,把回放契约一条条试出来(11 组,明细见
[`../knowledge/reasoning-wire-formats.md`](../knowledge/reasoning-wire-formats.md)):

- chat:开思考 + 缺 `reasoning_content` → 400;空串 → 200。
- responses:单轮工具不带 reasoning item → 200;**两轮**工具缺任一轮 → 400;
  用**重建**的最小 item(`{type:"reasoning",content:[{type:"reasoning_text"}]}`)→ 200。
- responses 的 `encrypted_content` 竟然是 `"<response_id>-0"`,是个指针不是密文。
- `reasoning.effort="none"` 能干净关掉思考(chat 侧对应 `thinking:{type:"disabled"}`)。

→ 关键结论:**这个项目的思维链从来不需要"不透明载荷"**,`reasoningSignature` 可以直接去掉。

### 改了什么

| 改动               | 前                                                   | 后                                         |
| ------------------ | ---------------------------------------------------- | ------------------------------------------ |
| 厂商               | deepseek / openai / anthropic                        | 只有 deepseek                              |
| wire               | chat(两方言)+ responses(两方言)+ messages            | chat + responses(无方言)                   |
| `AssistantMessage` | `content, reasoning, reasoningSignature, tool_calls` | `content, reasoning, toolCalls`            |
| `ToolCall`         | `{id, type:"function", function:{name, arguments}}`  | `{id, name, arguments}`                    |
| `ToolDefinition`   | `{type:"function", function:{…}}`                    | `{name, description, parameters}`          |
| 档位               | `off/low/medium/high`(medium 靠"不发字段"近似)       | `off/low/high/max`(与官方 effort 同名)     |
| 接线               | `main.ts` 内联                                       | `src/app.ts`(`AppLive`);`main.ts` 只剩一行 |
| 冒烟               | 无                                                   | `scripts/smoke.ts` + `pnpm smoke`          |

删除:`src/llm/anthropic.ts`(及其测试)、`src/llm/*Dialect`、`docs/knowledge/api/{openai,anthropic}.md`。

## 第二轮:内部模型换成 responses 的 item

**起因**:两条 wire 里 responses 表达力更强(item 化、内置工具、缓存),而内部模型原本是
message 形状 —— 于是主路径要"翻译",兼容路径反而直通,难度方向反了。

### 改了什么

| 改动         | 前                                                  | 后                                                                         |
| ------------ | --------------------------------------------------- | -------------------------------------------------------------------------- |
| 内部模型     | `ChatMessage` 联合(`AssistantMessage` / `tool` / …) | `Item`:`message` / `reasoning` / `function_call` / `function_call_output`  |
| 缺省 wire    | `chat`                                              | `responses`                                                                |
| LLM 领域位置 | `src/domain.ts`(与工具错误混放)                     | `src/llm/domain.ts`;工具/展示错误留在 `src/errors.ts`                      |
| 适配器契约   | `WireTransport` 接口 + 工厂返回 `{complete}`        | 直接 `complete(deps, items, tools)`;删掉 `wire.ts`(与 `LlmShape` 逐字重复) |
| chat 适配器  | `toWireMessage`(逐条消息)                           | `toWireMessages`(按"一轮回答"折叠 item)                                    |

测试里抓到过一个真 bug:折叠时先 `flush()` 再写正文,会把先到的 `reasoning` 丢掉
(`reasoning_content` 变成空串)—— 已修,并留了用例。

pnpm test   ✅ 4 文件 / 41 用例

## 第四轮:配置整体下沉到 llm

问题:`thinking` 与 `wireApi` 都只有 wire 适配器在用,却挂在"应用级 `AppConfig`"上 ——
顺带让 `llm/domain.ts` 反向 `import type { AppConfigShape }`,形成 config ↔ llm 的类型环。

改法:**删掉 `src/config.ts`**,LLM 的可调项收成 `LlmSettings`(在 `llm/domain.ts`),
读环境变量的 Layer 单独一层 `llm/settings.ts`:

| 变化       | 前                                    | 后                                                                            |
| ---------- | ------------------------------------- | ----------------------------------------------------------------------------- |
| 配置类型   | `AppConfigShape`(app 级)              | `LlmSettings`(llm 级:`wireApi` / `model` / `baseUrl` / `apiKey` / `thinking`) |
| 读环境变量 | `config.ts` 的 `AppConfigLive`        | `llm/settings.ts` 的 `SettingsLive`                                           |
| 依赖注入   | `LlmDeps { config, client }`          | `LlmDeps { settings, client }`                                                |
| 类型环     | `llm/domain.ts` → `config.ts`(类型级) | **消失**(llm 不再认识 config)                                                 |
| 接线       | `provide(AppConfigLive)(LlmLive)`     | `provideMerge(SettingsLive)(LlmLive)`(repl 要显示标题)                        |

没有"应用级配置"了:`NO_COLOR` 仍由 repl 直接读 `process.env`(它不是配置项,是终端能力探测)。

验证:`pnpm check` ✅ / `pnpm test` ✅ 41 用例 / `pnpm build` ✅ / `pnpm smoke` ✅
responses(默认)与 chat+thinking=max 两条真 key 路径都通。

### 第十轮:REPL 输入看不见(修 echo)

**症状**:在 REPL 里打字,屏幕上没有回显。

**根因**(读 `@effect/platform-node-shared/dist/NodeTerminal.js`):

```js
const rl = readline.createInterface({ input: stdin, escapeCodeTimeout: 50 }); // ← 没有 output
// ...
if (stdin.isTTY) stdin.setRawMode(true); // ← 关掉内核回显
```

`raw mode` 禁掉了终端自己的回显,而 readline 没有 `output` 就无法重绘输入行 —— 两头都不亮。
effect 的 `Terminal.readLine` 是为"自己渲染的 TUI"(按键流 + 自己画)设计的,不是行编辑器。

**修法**:`repl.ts` 换成 `node:readline/promises` 的 `question()`(提示符 / 回显 / 方向键 / 行编辑全归它),
顺带把 `runRepl` 的依赖从 `Agent | Terminal.Terminal` 降到 `Agent`。
提示符用纯文本(`REPL_PROMPT = "> "`,ANSI 会干扰 readline 的宽度计算)。

**第二个坑**:`pnpm dev` 原本是 `node --watch src/main.ts` —— 输入 `exit` 后进程不退出
(`Completed running ... Waiting for file changes`)。改成 `dev = node src/main.ts`,
另加 `pnpm watch` 给想自动重启的人。

验证:`printf "只回复 OK\n\nexit\n" | pnpm dev` 现在能正常出结果并以 exit=0 结束(以前会卡住)。

### 第十二轮:工具改成 `run` 的参数,内置工具降级为可选

问题:工具集是**装配期**定死的服务(`Toolbelt` Layer),agent 必须依赖它;想加/减/换工具就得改 Layer 图。

改法:**定义与执行都按次给**。

| 工具契约         | `Toolbelt` 服务(`definitions` + `execute(name, args)`) | `Tool` = `{ definition, execute(rawArgs) }`,放在 `agent/_domain.ts` |

`_domain.ts` 里也更干净了:`Tool` / `ToolbeltShape` 迁到 `agent/_domain.ts`,`Spawner` 留在应用层。

测试也跟着调整:agent 的用例直接传一个 stub 工具数组(不再需要 `Layer.succeed(Toolbelt, …)`);

### 第二十轮:item 助手改名 + 补 reasoning

被问到「`textOf` 是不是有特别用意」—— **没有,是起错了**。三个问题:

1. **两套命名规则混用**:`functionCallsOf` 跟 `Item.type`(`function_call`)走,`textOf` 却跟**字段名**(`text`)走;
2. **`textOf` 名不副实**:`reasoning` item 也有 `text` 字段,这个名字没说清它只取 `message`;
3. **reasoning 没有对应助手**:agent 里手写 `if (item.type === "reasoning")`。

改成一套规则:**按 `Item.type` 命名**,并补上缺的那一半。

| 之前                     | 之后                        | 返回                                 |
| ------------------------ | --------------------------- | ------------------------------------ |
| `textOf(items)`          | `messageTextsOf(items)`     | 各条 `message` 的文本数组(空串滤掉)  |
| —(手写 if)               | `reasoningTextsOf(items)`   | 各条 `reasoning` 的文本数组          |
| `functionCallsOf(items)` | 同名,内部改用泛型           | `function_call` item 数组            |
| `textsOf(parts, type?)`  | `partTextsOf(parts, type?)` | 名字点明处理的是 `WireResponsesPart` |
| —                        | `itemsOfType(items, type)`  | 泛型取值,返回类型自动收窄            |

约定写进 `AGENTS.md` 的「命名」: `xxxOf` 取 item、`xxxTextsOf` 取文本、wire 助手带上被处理的类型名。
调用方(agent 循环)因此少了两处手写 `item.type === …`,最终答复改成 `messageTextsOf(produced).join("")`。

行为无变化(两个适配器产出的 item 只有 `assistant` 消息),测试与真 key 冒烟均通过。

### 第二十七轮:查"报红" —— 查出一个真漏洞

用户让看整个项目哪里报红。逐层跑了一遍(`vp check` / `tsc` / `vp lint` / `tsgolint` / `test` / `build`),
**查出一个真的配置漏洞**:

```jsonc
// tsconfig.json(修前)
"include": [
  "packages/*/src/**/*.ts",      // ← 只匹配 packages/agent/src/**
  "packages/*/scripts/**/*.ts",
  "packages/*/vite.config.ts"
]
```

客户端搬到 `packages/client/<客户端>/` 之后,这条**单层 glob 匹配不到** `packages/client/*/src/**`,
于是 **repl / tui / web / desktop / mobile 五个客户端的源码全部没被类型检查**。
`vp check` 一直显示"全绿",其实只检查了 agent 包 —— 这是最危险的一类红:**看不见的红**。

修法:改成 `"include": ["packages/**/*.ts", "vite.config.ts"]`。修完后程序里多出 13 个客户端文件
(24 → 37 个自有文件),`tsc` 仍然 0 错 —— 说明代码本身是对的,只是以前没被检查。

顺带记录另一个**潜在**红点(还没修):

- **web 包没有 DOM lib**。根 tsconfig 是 `lib: ["ES2023"]`,实测在 web 包里写 `document.title` 会报
  `TS2584: Cannot find name 'document'`。等 web 真正开始写页面时,要么给根 tsconfig 加 `"DOM"`(简单,
  但会让 agent 代码也能误用 DOM),要么给 web 包单独一份 tsconfig(干净,但根 `vp check` 就不再覆盖它)。

另外澄清一个"假红":直接跑 `tsgolint`(默认规则集)会报 52 条(其中 31 条是 `prefer-readonly-parameter-types`),
但项目的 lint 配置是 `plugins: ["typescript", "oxc"]`,`vp lint` 为 0 告警 —— 编辑器若直连 tsgolint 默认规则
才会看到这些,不属于项目门禁。

门禁现状:`pnpm check` ✅(66 文件)/ `tsc` 0 错 / `pnpm test` ✅ 45 用例 / `pnpm build` ✅ 4 个包 /
`pnpm dev`、`pnpm smoke`、三个占位入口均正常;无 TODO / FIXME / `@ts-ignore`。
