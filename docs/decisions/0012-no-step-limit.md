# 决策:不设工具调用次数上限

> 已接受 · 2026-10-24 · 取代 `_constants.ts` 里 `MAX_STEPS = 12` 的隐含策略 ·
> 落点 `packages/agent/src/loop/` · 设计见 [`../designs/agent/loop.md`](../designs/agent/loop.md)

## 矛盾

旧循环用 `MAX_STEPS = 12` 防死循环:一轮里生成 12 次后,不再调模型,直接返回

```
(已达到最大步数 12,任务可能未完成)
```

这条兜底有三个问题:

| 问题                 | 说明                                                                            |
| -------------------- | ------------------------------------------------------------------------------- |
| 截断合法任务         | "读 30 个文件再汇总"这类任务第 12 步本来还没做完                                |
| 返回的不是模型的回答 | 字符串由内核伪造,`ask` 的调用方会把它当成答案;transcript 里也没有对应 assistant |
| 把策略写死在内核     | 上限应该是成本 / 时间策略,不同客户端、不同任务的合理值不一样                    |

## 处理

- 删掉 `MAX_STEPS`、`Turn.steps` 和"达到上限就返回提示"的分支;
- 循环只在两种情况下停:
  1. 模型这一轮**没有** tool call(正常结束,回答交给 `ask`);
  2. 引擎被中断(客户端 `Fiber.interrupt` / 关 scope)。
- 测试从"12 步兜底"改成"20 轮工具调用后仍能拿到最终回答",防止以后又偷偷加回上限。

## 为什么

- **引擎不该伪造答案**:要停就停,不要用一句假回答掩盖"没做完"。
- **停止机制已经存在**:`Agent.run` 的 fiber 生命周期归调用方,REPL 的 Ctrl-C、web 的 reset、
  进程退出都能停下;再叠一个固定步数没有新增控制力,只增加误伤。
- **成本是另一件事**:按步数限流既不准(每步 token 差异很大)也不该由内核替用户决定;
  真要做预算,应该按 token / 时间 / 金额,并且可配置。

## 代价

- **可能真的转不停**:模型反复"调工具 → 看到结果 → 再调工具"时,会一直烧 token,
  `ask` 也一直不返回;没有自动兜底。
- **transcript 在一轮内也可能无限增长**,没有上下文压缩,最终可能撞模型上下文上限并报错。
- **客户端必须提供中断手段**:REPL 有 Ctrl-C,web 有 reset;一次性脚本如果忘了设超时,
  可能挂到进程被杀。

## 复查条件

1. **真的出现跑飞的会话 / 账单异常**:加**会话级预算**(最大 token、wall-clock 截止时间或金额),
   做成可配置;不要恢复固定步数。
2. **客户端需要"尽力而为"的截断答案**:把上限放到客户端策略里(比如客户端自己的 `runTurn` 外面套
   `Effect.timeout`),内核仍不伪造回答。
3. **一轮 transcript 大到必然超上下文**:先做压缩 / 截断,再谈上限;
   压缩时不能把 `function_call` 与它的 output 拆开。
4. **工具本身变慢或计费**:优先给工具加超时 / 审批,而不是限制调用次数。
