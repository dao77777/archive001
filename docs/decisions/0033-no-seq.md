# 决策:去掉 `seq`,文件行序就是顺序

> 已接受 · 2026-10-24 · 细化 [`0032`](0032-flat-archive-entry.md)
> (扁平 Entry 不变)· 落点 `packages/agent/src/archive/` · 设计见
> [`../designs/agent/archive.md`](../designs/agent/archive.md)

## 矛盾

0032 给每条 `ArchiveEntry` 加了 `seq`(进程内自增)。但:

- archive 是单 writer、append-only 文件,**文件行序已经是一个全序**;
- `seq` 在 `Agent.publish` 里、入队之前分配,和真正的入队顺序可能不一致
  (两个 fiber 可以先拿到 1/2,再以 2/1 的顺序入队);
- 进程重启后 `seq` 从 1 开始,和旧文件重复;多进程更是各数各的。

结果是:`seq` 既不是可靠的全序,也不是稳定的跨重启游标,只是多了一份会骗人的数字。

## 处理

- 删除 `ArchiveEntry.seq`;
- 顺序由**文件行序**决定;
- 保留 `v`(格式版本)和 `at`(写入时间,只做诊断);
- `Agent.publish` 只补 `v / at`,不再维护计数器;
- 需要定位某条记录时,用行号 / 字节偏移 / `event.id`,而不是 `seq`。

## 为什么

- **单一事实来源**:顺序只有一个,就是写入顺序;不要再造第二个可能不一致的序号。
- **避免假精度**:一个会跨重启重置、会和入队顺序错开的 `seq`,比没有更危险。
- **单 writer 不需要序号**:append-only 文件天然按行排序。
- **`at` 不承担排序**:它只是"大概什么时候写的",时钟回拨也不影响日志顺序。

## 代价

- **不能直接用 `seq` 做游标**:续读要记录行号 / 字节偏移,或者先读全文件。
- **不能靠 `seq` 检测缺行**:要检测完整性,需要文件级校验(行数 / hash 链)。
- **将来多 writer 会需要顺序号**:到那时必须由**单写者**在写入时分配,并和文件顺序一致。

## 复查条件

1. **多进程 / 多 writer 共用 archive**:加文件锁,并由单写者在写入时分配 `seq`;
   实时流如果需要 seq,要等写入后再发,或接受实时流没有 seq。
2. **需要断点续读**:用行号 / 字节偏移作为游标;不要恢复进程内计数器。
3. **需要完整性校验**:加 hash chain(`prevHash`)或文件尾校验,而不是 seq。
4. **需要稳定的事件引用**:用 `event.id`;它已经存在,且和顺序无关。
